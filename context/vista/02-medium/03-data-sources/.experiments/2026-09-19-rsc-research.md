# RSC candidate research — source-verified findings — durable evidence

This durable copy records evidence established on 2026-09-19 in the disposable Vista data bakeoff at `tmp/vista-data-bakeoff/rsc-research.md`; the working code lived beside that source report and is not part of the VRS.

## Question

What the current Vite RSC stack guarantees and how it collides with Vista's extraction, Schema, and publish invariants.

## Method

Primary documentation and installed-source analysis covered plugin versions, Flight serialization, Effect realms, extraction, StyleX, and adjacent server-function approaches.

## Result

RSC can pre-render Flight and HTML, but Flight is a tree protocol rather than a Schema-readable domain snapshot, and the existing collector cannot run in a react-server realm.

## Conclusion

RSC can pre-render Flight and HTML, but Flight is a tree protocol rather than a Schema-readable domain snapshot, and the existing collector cannot run in a react-server realm.

## VRS Impact

Keep RSC out of the data foundation; treat it only as a possible future render transport beside the existing data plane.

# RSC candidate research — source-verified findings

## 1. `@vitejs/plugin-rsc` status (Vite 8 / React 19.2 / prerender / wire format)

**Version & Vite 8.** Repo `main` `packages/plugin-rsc/package.json` is `"version": "0.5.35"` (raw.githubusercontent.com/vitejs/vite-plugin-react/main/packages/plugin-rsc/package.json); GitHub release `plugin-rsc@0.5.35` dated 2026-09-16 (github.com/vitejs/vite-plugin-react/releases). npm's `latest` tag reported as 0.5.28 in one search snapshot — tag may lag; treat 0.5.35 as current. Built on the Vite environment API with `rsc`/`ssr`/`client` environments (README "Basic Concepts"); peer `vite: "*"`, works on Vite 8.0.x.

**React 19.2 peer requirement: none (but version-lock `react-server-dom-webpack`).** `peerDependencies: { react: "*", react-dom: "*", react-server-dom-webpack: "*" (optional) }` (same package.json). The plugin ships a **vendored `react-server-dom-webpack`** — the Flight package is `react-server-dom-webpack`, not `react-server-dom-vite`/`-node` — and "When `react-server-dom-webpack` is installed in your project's dependencies, the plugin will automatically use it instead, allowing you to use any React version you need" (README, "Using different React versions", worked example pinning react/react-dom/react-server-dom-webpack to 19.2.3). `react-server-dom-webpack@19.2.8` exists on npm (latest, ~Aug 2026; npmjs.com/package/react-server-dom-webpack), so the hoisted `react@19.2.8` pairs cleanly. (Earlier 19.x lines were deprecated for RSC security fixes — expo.dev/changelog/mitigating-critical-security-vulnerability-in-react-server-components, Dec 2025.)

**Static pre-render of Flight payloads: yes.** `@vitejs/plugin-rsc/rsc/static` provides `prerender` — "static RSC serialization (React VDOM -> RSC stream)" based on `react-server-dom/static.edge`; Node variant `rsc/static.node` → `prerenderToNodeStream` (README, "RSC runtime (react-server-dom) API"). `examples/ssg` proves the full publish shape: a `buildApp` plugin imports the built rsc entry, calls `entry.handleSsg(request)` returning `{html, rsc}` streams, and writes both `<path>.html` and `<path>_.rsc` into the client outDir (examples/ssg/vite.config.ts). React counterparts: `react-dom/static` `prerender`/`prerenderToNodeStream`/`resumeAndPrerender` (react.dev/reference/react-dom/static). "Publish = pre-rendered Flight payload + SSR HTML as snapshot" is a supported, example-backed path.

**Flight wire format — serializable value set** (react.dev/reference/rsc/use-client, "Serializable types returned by Server Components"):
- Serializable: primitives (string/number/bigint/boolean/undefined/null, `Symbol.for`-registered symbols); iterables (String, Array, Map, Set, TypedArray, ArrayBuffer); Date; **plain objects created with object initializers**; Server Functions; Client/Server Component elements (JSX); Promises.
- **Not supported: "Classes … Objects that are instances of any class (other than the built-ins mentioned) or objects with a null prototype", non-exported functions, non-registered symbols.**

Consequences: **plain JSON survives intact** (primitives + object-literal records/arrays are first-class), so a `Schema.encodeUnknown` payload crosses cleanly and re-decodes on the client — single-decode symmetry is *possible*. **Custom classes cannot cross** — Effect `Schema.Class` instances must be encoded to plain records before the boundary; Flight has no custom-serializer hook for arbitrary classes (only server/client reference registration and `temporaryReferences`).

**Prior art: Schema-validating RSC props at the boundary — none first-class.** No mechanism in React or plugin-rsc validates a schema at the server→client crossing. What exists: (a) userland Zod "validateForClient" prop wrappers; (b) `rsc-contract` — *static analysis* of which modules/values cross the boundary, payload size, regression baselines (github.com/modeusweb/rsc-contract); (c) CapsuleRSC — TS types + ESLint + runtime `assertSerializable` (serializability guard, not a domain schema); (d) React's `experimental_taintObjectReference` (leak prevention, not validation); (e) TanStack's own RSC implementation emphasizes "hardened serialization, validation" at the boundary (tanstack.com/blog/react-server-components, Apr 2026). Verdict: any Effect-Schema-at-boundary discipline would be Vista-authored convention, identical in kind to the current `freeze.ts` encode.

## 2. Effect + RSC (module realms, Symbol identity, AsyncLocalStorage, RPC-as-transport)

**Module realms / identity.** React warns: "a single module may be evaluated on the server when imported from server code and on the client when imported from client code" (react.dev/reference/rsc/use-client, Caveats). Under plugin-rsc there are up to *three* evaluations (rsc, ssr, client); each environment gets its own module instance, so `effect`'s `Schema.Class` constructors, `Context.Tag`s, and singletons are **not identical across environments** — cross-realm `instanceof`/tag equality fails. Mitigation in practice: never pass instances across the boundary — encode → plain JSON → decode per realm (which the serializable-set rules force anyway). Vista already manages the two-realm version: decision 0027 requires "Effect packages must stay in Vite `ssr.external` so provider modules share one `effect`/`@effect/rpc` realm with the host" (context/vista/.decisions/0027-data-layer-schema-spine-two-tier-rpc.md, Consequences). Under plugin-rsc that config must be repeated per environment (`environments.{rsc,ssr}.resolve`); the client bundle inevitably carries its own `effect` copy.

**Symbol identity.** Flight only serializes `Symbol.for`-registered symbols (use-client doc); unique `Symbol()` values can't cross. In dev, rsc+ssr environments share the Node `globalThis`, so `Symbol.for` registries hold; across the network they don't.

**AsyncLocalStorage — the concrete known issue, now fixed.** GHSA-38f7-945m-qr2g / CVE-2026-32887: "When using `RpcServer.toWebHandler` … inside a Next.js App Router route handler, any Node.js `AsyncLocalStorage`-dependent API called from within an Effect fiber can read another concurrent request's context" — Effect's `MixedScheduler` drained all fiber continuations in one callback's ALS context. Affected `effect <= 3.19.15`, **patched >= 3.20.0** (github.com/Effect-TS/effect/security/advisories/GHSA-38f7-945m-qr2g). Vista's `effect@4.0.0-rc.112` (node_modules/effect/package.json) is post-fix. Residual lesson: hosting an Effect runtime inside an RSC request handler is supported-but-fragile — keep ALS-dependent framework APIs out of fibers.

**`@effect/rpc` as Flight transport: must sit beside, not under.** A Flight stream is only decodable through the plugin's generated client manifest: the browser entry uses `createFromReadableStream` from `@vitejs/plugin-rsc/browser`, which resolves client-reference ids → client chunks via build/dev manifests (README "RSC runtime API" + Basic Concepts diagram). Tunneling Flight bytes through `@effect/rpc`'s JSON protocol would strand those references. Shape: the standing service serves `.rsc` responses (rsc-env handler) **and** `/_data/<id>` RPC endpoints — Vista's existing `server.ts` pattern with one more route family. RPC stays the schema-typed data plane; Flight is the tree plane. (Effect 4 also ships its own typed server-function layer — see §4.)

## 3. Collisions with Vista's existing invariants

### (a) `extractSemanticManifest` under an RSC render — what concretely breaks
File: `flakes/vista/blocks/src/authoring.tsx` (360 lines).

1. **The render API can't load in the rsc environment.** Line 3: `import { renderToStaticMarkup } from 'react-dom/server'`. Under the `react-server` condition that module is a hard throw: `node_modules/react-dom/server.react-server.js:3-5` — `'react-dom/server is not supported in React Server Components.'`
2. **The collector context cannot exist in server components.** Line 31 `createContext`; consumed via `useContext` in `AppRoot` (~L40), `AddressableNode` (~L118), `Section` (~L150), `Decision` (~L190), `RuntimeIsland` (L230), `Ref` (~L258), `useDataBinding` (L271). react.dev: "Server Components cannot create context, but they can render a context provider imported from a Client Component module" (react.dev/reference/rsc/server-components). Decisive local proof — the react-server build of `react@19.2.8` exports only `use`, `useCallback`, `useDebugValue`, `useId`, `useMemo` (+`cache`/`cacheSignal`); **no `createContext`, no `useContext`** (node_modules/react/cjs/react.react-server.development.js, `exports.*` assignments at L832–846). Every marker component and the `useDataBinding` seam (L268–275, pushes into `context.node.bindings`) breaks as a server component.
3. **Render-phase mutation + single-pass assumption.** The collector works by side effects during render (`context.collector?.nodes.push(node)` in AppRoot ~L46 and each marker; `refs.push` ~L262; `bindings.push` ~L273). `renderToStaticMarkup` is one synchronous pass; a Flight render is streaming and may re-render subtrees across Suspense retries — collector pushes could duplicate, and nothing today dedupes.
4. **DOM↔manifest correspondence is same-render.** L339–346 regex `data-vista-id="…"` out of the *same* HTML the render produced, requiring exactly-one matches. Under RSC, HTML comes from a *separate ssr-environment* render of the Flight payload (README diagram: rsc env → Flight stream; ssr env → HTML; browser → hydrate), so manifest (rsc pass) and HTML (ssr pass) are two trees that must be reconciled explicitly.
5. **Async data components hide their subtree from a sync extractor.** react.dev on `renderToStaticMarkup`: "has limited Suspense support. If a component suspends, `renderToStaticMarkup` immediately sends its fallback as HTML" (react.dev/reference/react-dom/server/renderToStaticMarkup, Caveats). The rsc candidate's primitive is async server components that fetch — the fallback, not the children, is what a retained `renderToStaticMarkup` extractor would see. (Locally, Fizz only *suspends* on thenables — `spawnNewSuspendedRenderTask`, node_modules/react-dom/cjs/react-dom-server.node.development.js:7055 — it never blocks a static render.)
6. **RuntimeIsland suppression becomes redundant-but-harmless.** L245 `{context.collector === undefined ? children : undefined}` prevents island children executing in Node; `'use client'` client references give the same guarantee natively. But `useDataBinding`-style seams inside a client island can never reach the collector (context doesn't cross `'use client'` boundaries).

**Coexistence answer (the brief's key question):** the *current mechanism* cannot run inside an RSC render; it survives only as (i) a **separate classic-SSR render in a non-react-server realm exactly as today** — viable only while data components stay *synchronous in both realms* (declare-binding when extracting, fetch when serving; one module, two behaviors per environment, which RSC dual-evaluation permits), or (ii) a **rewrite against Flight `prerender`** (async, settle-all, scan the Flight model instead of HTML-regex, cross-check against ssr-env HTML). Option (ii) rewrites authoring.tsx's collector; option (i) keeps authoring.tsx untouched but forces every data component to remain sync-renderable.

Freeze-symmetry clause: "Draft and published render through one path (no `vite build` for reviews); what you preview is what you freezes."
- **0075** (`0075-published-versions-are-self-contained-static-directories.md`): published versions are **built once at publish** with the repo-pinned Vite toolchain — content-addressed JS/CSS/assets + schema-versioned semantic manifest + receipt; serving is generic static, "never falls back to source evaluation or Vite"; "Draft authoring may continue to use Vite/HMR, and drafts are the only live-serving surface."
- **Under RSC:** publish output naturally matches 0075 — the ssg example's `.html` + `.rsc` + client chunks slot into the receipt inventory; serving needs zero data calls (its `appType: 'mpa'` preview echoes Vista's nested MPA layout). Changes: (1) Vite config grows three environments (`rsc`/`ssr`/`client` entries) and the plugin's rsc-handler beside existing service routes — the rejected Rolldown *bundled-dev* stays rejected, but plugin-rsc's rsc environment is exactly the per-request server rendering 0052 kept, now condition-split; (2) **draft/published divergence returns at payload level**: draft = live rsc-handler Flight render, published = publish-time `prerender` Flight — 0052's "what you preview is what you freeze" now holds only up to render-input identity, since two renders produce the two payloads; (3) provider mounting via `ssrLoadModule` (0027) coexists, but per-environment `resolve.external` for `effect`/`@effect/rpc` must include the rsc env to preserve one server-side effect realm; (4) the client dep-optimizer gains plugin-rsc's vendored `react-server-dom` entries in `optimizeDeps.include` (README "framework package" section) — new surface next to GA auto-discovery. Net: 0075 *strengthened* (Flight+HTML are static artifacts); 0052's one-path freeze-symmetry *weakened* (prerender is a second render at publish).

## 4. RSC-adjacent alternatives worth naming

**TanStack Start `createServerFn` with validators.** Server functions are same-origin RPC endpoints; `.validator()`/`.inputValidator()` accepts Zod/Valibot/ArkType via **Standard Schema** out of the box, "unvalidated requests are rejected at the network boundary", and TS `strict` mode checks *both* input and output serializability (tanstack.com/start/latest/docs/framework/react/guide/server-functions). **Effect Schema is native here**: `Schema.toStandardSchemaV1` exists in effect 4 (node_modules/effect/dist/Schema.js:467, vendor `"effect"`), so a provider op is `createServerFn().inputValidator(Schema.toStandardSchemaV1(Args))`. Mapping to Vista: freeze = invoke at publish + `Schema.encode` into `snapshot.json` (the existing `freeze.ts` keystone unchanged); refresh = call the server fn again — **per-op granularity, works from any static page** (it's just fetch). Caveat: runtime validation is *input-only* — outputs are TS-serializability-checked, not schema-decoded — so live/frozen single-decode needs a small client-side decode wrapper. TanStack also ships its own RSC mode (tanstack.com/blog/react-server-components).

**Remix / React Router 7 loaders.** RR7's RSC support is explicitly unstable — "experimental and subject to breaking changes" — and is built *on* `@vitejs/plugin-rsc` (`unstable_reactRouterRSC()` + `rsc()`; reactrouter.com/how-to/react-server-components). The non-RSC loader model maps to the `loader` candidate: loaders may return React elements (rendered only on the server) alongside data. Effect Schema is not native — loader results are typed by typegen over turbo-stream single-fetch serialization; a schema decode must be hand-placed. Publish-freeze maps (loader runs at publish, encode to snapshot), but refresh granularity is whole-route/whole-app (`router.reload()`/revalidation), and adopting RR7 the framework would displace Vista's own shell — pattern inspiration, not adoption.

**Astro islands + content collections.** Strongest *build-time-schema* story: each collection declares a zod schema; "a malformed frontmatter field fails the build loudly, with a path to the offending file, before a single HTML file is written" — schema-at-the-freeze-boundary as a framework primitive (docs.astro.build/en/guides/content-collections/; "live collections" validate at runtime with the same zod schemas). Mapping: publish = static HTML by construction (near-perfect 0075 alignment); viewers are islands; refresh = an island calling an Astro Action (zod input schema) or API endpoint — per-block granularity. But Effect Schema is second-class (`astro:content` is zod-shaped), and Vista would surrender React-tree authoring for the static half — worth naming mainly as proof that build-time schema-validated snapshots are an established pattern.

**Effect's own `HttpApi`/`RpcGroup` as the typed server-function layer.** Not an alternative so much as the incumbent: decision 0027 fixes "effect `Schema` is the non-negotiable contract spine" + two-tier `@effect/rpc` (`provider.ts` `defineProvider({id, group: RpcGroup, core})`, `core[op]` in-process for `freeze()`), and effect 4 ships `effect/unstable/httpapi` and `effect/unstable/rpc` natively (node_modules/effect/package.json exports). An `RpcGroup` *is* a typed server-function layer with runtime Schema decode on both ends and `toWebHandler` hosting (the GHSA advisory's repro shows `Rpc.make("GetUser", { success: S.Struct(…) })` via `RpcServer.toWebHandler`). Schema sits at the boundary *natively on both tiers*; freeze/refresh is exactly Vista's current `runFrozen`/`runLive` split; what it lacks vs RSC is server-side tree composition (no async server component rendering with the data) — the tree must still be authored client-side with the fetched value. The `query` candidate is essentially this layer done better; the honest RSC comparison is "Flight for the tree + this layer for the data" vs "this layer alone".

## Re-testing the June claim (brief: "RSC = opaque result blobs")
`context/vista/02-medium/03-data-sources/.experiments/2026-06-20-data-layer-research.md` rejected RSC because frozen payloads "need codegen to re-decode." **Mostly confirmed, with one important carve-out.** Confirmed: a frozen `.rsc` payload interleaves React elements, client references, and promises — no schema hook exists inside React's boundary (§1 prior art), so re-validating "the data" from a Flight stream requires a Flight parser, not a `Schema.decode`. Carve-out: since custom classes can't cross anyway, a server component must hand client islands *plain-JSON* props — if Vista keeps `snapshot.json` (Schema-encoded at publish, `freeze.ts`-style) as the snapshot of record and treats Flight purely as the render/transport layer for the tree, single-decode symmetry survives untouched. The candidate is viable only under that discipline: **Flight is the tree plane, never the data snapshot.**
